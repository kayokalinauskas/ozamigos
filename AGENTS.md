# AGENTS.md — guia para agentes de código

Este arquivo explica o projeto para quem vai mexer no código (pessoas ou agentes). O `README.md` é para quem usa e publica; aqui ficam as regras, os contratos e as armadilhas.

## O que é

Ozamigos: transmissão de tela de jogos entre amigos, em 720p a 30 fps, **P2P por WebRTC**.

São três peças num repositório só:

| Pasta | Tecnologia | Papel |
|---|---|---|
| `src/` | Java 25, Spring Boot 4.1 (Jackson 3: `tools.jackson.*`) | Salas, senha do grupo, sinalização por WebSocket em `/sinal`. **O vídeo nunca passa por aqui.** Serve a interface pronta |
| `web/` | React 19, TypeScript 7, Vite 8 | Interface. O build vai para `src/main/resources/static/` (não versionado) |
| `desktop/` | Electron 44 + auxiliares C# (.NET 10) em `desktop/som/` e `desktop/captura/` | App Windows: carrega a interface **do servidor** (`loadURL`) e acrescenta seletor de fontes, uma captura de vídeo própria, som do PC sem Discord, notificações |

Deploy: Render (Docker). O `Dockerfile` tem 3 etapas: Node monta `web/`, o JDK compila, e a imagem final roda no JRE. O Render publica a cada push na `main`.

## Convenções do projeto (siga sempre)

- **Idioma:** código, identificadores, comentários, mensagens de commit e textos da interface em **português do Brasil**. Os comentários explicam o *porquê*, no tom dos já existentes.
- **Commits:** adicione **caminhos explícitos** (`git add caminho/arquivo`), nunca `git add -A` ou `git add .`. Faça push só quando pedirem.
- **Terminal do dono:** é o PowerShell 5.1, que **não aceita `&&`**. Nas instruções para ele, use um comando por linha ou `;`.
- **Testes:** poucos e essenciais, um por comportamento que importa (pedido do dono). Rode `.\testar.ps1` antes de commitar (servidor, interface, áudio, ponta a ponta e app; a seção "Testes" do README explica cada camada). Mudança de comportamento ganha teste na camada certa; o resto se verifica rodando o app (veja "Como testar").
- **Telas prioritárias:** 1920×1080 e 2560×1440. A interface é tema escuro, com os tokens CSS em `web/src/estilo.css`.
- **Celular (navegador):** quem usa é quem assiste. **Nada pode passar da largura da tela**: no celular, um elemento mais largo estica a página inteira e aparece rolagem de lado (aconteceu com a fileira de baixo, até 14/10/2026). As regras ficam no `@media (max-width: 640px)` do `estilo.css`, e o teste e2e "no celular, nada passa da largura da tela" confere. Em fileira com `flex`, lembre do `min-width: 0`: sem ele, um `select` deixa o grupo da largura da opção mais comprida. Textos para quem não está no app não falam em "Windows" (`Padrão do sistema`).
- **Tom de produto** (pedido do dono, 17/10/2026): o Ozamigos é tratado como produto, mesmo sendo hoje de um grupo de amigos. **No app e no site, os textos não explicam como ele funciona por dentro nem onde está hospedado:** nada de "servidor gratuito", "dorme", Render, Cloudflare, STUN/TURN, WebRTC, P2P, RNNoise, "rede neural", kbps ou medidas de bancada. Diga o benefício ("pouco atraso", "redução de ruído inteligente", "só chega a quem clicar em Assistir"). Os detalhes técnicos ficam no GitHub (README, AGENTS, CHANGELOG), no máximo. As exceções são as telas de diagnóstico (painel de estatísticas, relatórios, teste de desempenho), que são técnicas de propósito.
- **Estatísticas de uso:** o dono quer poder coletar estatísticas técnicas (desempenho, qualidade das conexões) para melhorar o app, com o usuário avisado no app, como os grandes. Por isso o site não promete "sem rastreamento" nem "sem ferramentas de análise"; a privacidade diz que o app avisa quando usar estatísticas, e que o conteúdo das conversas nunca entra nelas. **Hoje nada é coletado:** se isso mudar, o aviso no app vem junto, e o texto da privacidade nas duas línguas também.
- **Segredos:** a senha do grupo vem só da variável `OZAMIGOS_SENHA`. Nunca coloque segredos no código. Ela é comparada pelo resumo SHA-256 (`SenhaDoGrupo`): comparar as senhas direto com `MessageDigest.isEqual` deixava o tempo da resposta contar o tamanho dela.

## Arquitetura e contratos importantes

### Servidor (`src/main/java/dev/ozamigos/`)

- `Salas`: estado **em memória**, com todos os métodos `synchronized`.
  - Cada sala guarda `participantes` (id → sessão), `nomes` e `plateias` (quem transmite → quem assiste).
  - **Existir uma chave em `plateias` é o que significa "está transmitindo".**
  - Limite: `LIMITE_POR_SALA = 8` (eram 5 até 13/10/2026). O gargalo não é o servidor: quem transmite manda uma cópia (e uma codificação na placa) para cada pessoa que assiste, ~4 Mbps cada em 720p. Com 7 assistindo, são ~28 Mbps de upload; acima de 8, seria preciso limitar quantos assistem cada transmissão.
- `SinalizacaoHandler`:
  - **a senha é conferida antes de tudo**; quem erra recebe `senha-errada` e a conexão é fechada;
  - **freio de senhas** (`TentativasDeSenha`): 10 erros do mesmo endereço em 5 minutos bloqueiam o endereço (`muitas-tentativas`). O endereço é o `CF-Connecting-IP`, que a Cloudflare (na frente do Render) escreve e o visitante não consegue forjar (`SinalizacaoHandler.endereco`); sem ele, o endereço remoto. **Não volte para o `X-Forwarded-For`**: ele começa pelo que o visitante quiser, e forjá-lo a cada tentativa escapava do freio (o teste `forjarOXForwardedForNaoEscapaDoFreioDeSenhas` cobre isso). Se o servidor sair de trás da Cloudflare, o `CF-Connecting-IP` passa a poder ser forjado: troque a regra junto.
  - o `entrou` vai só para quem já estava quando a pessoa entrou (`Entrada.avisar`, tirado junto com a lista do `bem-vindo`, dentro do `synchronized`). Com a lista tirada depois (`salas.outros`), duas pessoas entrando juntas (todos voltando depois de um deploy) faziam uma aparecer duas vezes para a outra;
  - o servidor **carimba `de`** em tudo o que repassa (o cliente nunca diz quem é) e só repassa dentro da mesma sala;
  - os envios usam `ConcurrentWebSocketSessionDecorator` (a sessão "segura");
  - **chat da sala** (`chat` em `SinalizacaoHandler`): só repassa para todos da sala, inclusive quem mandou (é a confirmação de que chegou), e **não guarda nada** (decisão do dono: nada de histórico; quem entra depois não vê o que foi dito). O texto é limpo por `textoDoChat` (sem caracteres de controle nem os de direção do texto, até `CHAT_MAXIMO` = 500), com freio de `CHAT_RAJADA` (5) a cada `CHAT_JANELA_MS` (3 s) por conexão. **O texto do chat nunca vai para o log do servidor.**
- `WebSocketConfig`: **sem `setAllowedOrigins`**. Só páginas do próprio servidor conectam; o app Electron funciona porque carrega a interface do servidor. Mensagens de texto vão até 64 KB.
- Protocolo completo: seção "Protocolo de sinalização" do `README.md`. **Se mudar o protocolo, mude o servidor, os tipos em `web/src/conexao/protocolo.ts` e o README juntos.** O teste `conexao.test.ts` falha se o servidor mandar uma mensagem ou um erro que o `protocolo.ts` não conhece, e o `switch` de `tratar` no `cliente.ts` não compila sem um caso para cada mensagem.

### Interface (`web/src/`)

- `cliente.ts` é o núcleo, sem React: um *store* com `inscrever`/`ler` consumido por `useSyncExternalStore` (`useCliente`). Os componentes só leem o estado e chamam as ações.
- As peças do núcleo ficam em `conexao/`, sem estado da sala: `protocolo.ts` (as mensagens), `sinalizacao.ts` (o WebSocket, a fila de mensagens e as esperas da reconexão), `captura.ts` (getDisplayMedia e codificador por qualidade), `medidor.ts` (as `Metrica` de cada segundo), `relatorio.ts`, `webrtc.ts` (STUN, Opus no SDP, a preferência de codec, candidatos tolerantes) e `codigoDaSala.ts`. A voz usa as mesmas de `webrtc.ts`.
- **Duas conexões por par, uma por sentido:** a chave é `${canal}:${id}`, com `canal` igual a `'envio'` (minha tela para a pessoa) ou `'recebimento'` (a tela dela para mim).
  - O candidato ICE carrega o `canal` **do ponto de vista de quem mandou**, e quem recebe inverte (`envio` ↔ `recebimento`). Não remova essa inversão.
  - Quem transmite **sempre** é quem faz a oferta; isso evita colisão de ofertas (*glare*).
- **Assistir sob demanda:**
  1. quem quer assistir manda `assistir {para}`;
  2. o servidor põe a pessoa na plateia, avisa quem transmite (`assistir {de}`) e manda `plateia` para todos;
  3. quem transmite cria a conexão de envio e faz a oferta;
  4. quem assiste só aceita a oferta se ainda estiver em `estado.assistindo`.
- **`assistindo` é intenção, não conexão:** a pessoa continua na lista quando quem transmite para. Quando chega `compartilhando` dessa pessoa, o cliente manda `assistir` sozinho (volta automática). A pessoa só sai da lista com `deixarDeAssistir` ou com `saiu`.
- **Trocar a fonte não renegocia:** a conexão é sempre criada com um *transceiver* de áudio (mesmo sem áudio no momento), e a troca usa `replaceTrack`.
- **Qualidade: 720p a 30 fps por padrão** (`QUALIDADE` em `qualidade.ts`, id `leve`), **com 720p e 1080p, a 30 e a 60 fps, escondidos na engrenagem do app** (aba Geral, `SecaoDaQualidade` em `Configuracoes.tsx`; ids `leve60`, `nitida` e `nitida60`; guardada em `ozamigos-resolucao`, que fica vazia no padrão). Histórico: em 14/10/2026 a escolha saiu (decisão do dono: em jogo pesado a captura do Chromium não passava de ~21–29 fps, o 1080p nunca rendeu de verdade e dobrava o custo, e 720p · 30 é o que o grupo usava no Discord sem Nitro), junto com a descida automática de 1080p para 720p (`qualidadeAutomatica.ts`); a chave antiga, `ozamigos-qualidade`, continua sendo apagada ao abrir. **Voltou em 17/10/2026, também a pedido do dono**, com a captura do app (1.2.18), que custa o mesmo em 1080p e em 720p: só no app, longe da tela principal, com a ressalva do custo (internet de envio por amigo e placa de vídeo) quando não é o padrão. **O padrão continua 720p · 30: não mude sem o dono pedir, nem traga a escolha para a tela principal.**
  - A escolha vale **a partir da próxima vez que a pessoa escolhe o que transmitir** (`transmitir` em `cliente.ts` lê `qualidadeEscolhida()` e passa à captura, a do app ou a do Chromium; só depois de capturar ela vira `estado.qualidade`, que o codificador e os relatórios usam). Trocar no meio refaria a captura do app.
  - Bitrates: 1080p com o dobro do 720p (2,25 vezes os pixels, e o H.265 rende mais por bit), 60 fps com 1,5 vez o de 30. **Medido no app** (17/10/2026, a tela inteira para um Chromium, só o vídeo do Firefox se mexendo): 1920×1080 chegando; a 60 fps, 46–53 fps (a captura do app só manda quadro quando a imagem muda) e nenhum congelamento em 25 s, em 720p · 60 e em 720p · 30. Uma troca de fonte que muda a resolução no meio custa alguns congelamentos para quem assiste (o vídeo dele se reajusta). **Ainda não medido:** 1080p e 60 fps com o jogo e com amigos de verdade, na internet.
  - o **tamanho e o fps saem da captura** (`tamanhoDaCaptura()`, no `getDisplayMedia` e no `applyConstraints`): o navegador reduz a imagem uma vez só, e não um codificador por amigo. Por isso `scaleResolutionDownBy` fica sempre em 1;
  - o codificador recebe `maxBitrate`, `maxFramerate` e `degradationPreference` por `setParameters` (`aplicarNoEnvio`).
  - **"Diminuir em vez de travar" é do próprio WebRTC:** `degradationPreference: 'maintain-resolution'` faz cada codificador baixar o fps e a nitidez quando falta processador ou banda, **sem mexer na resolução** (o mesmo do LiveKit, base do Stoat, para tela). Como cada pessoa assistindo tem a sua conexão e o seu codificador, isso já acontece **por pessoa**, sem código nosso.
    - Até 14/10/2026 era `'balanced'`, que cortava a resolução. Em jogo pesado ela não voltava: o WebRTC só sobe a resolução quando a imagem fica fácil de codificar (QP baixo), e o `qualityLimitationReason` mostra isso como `bandwidth` mesmo com banda sobrando. Dois relatórios reais (Path of Exile, para um celular e para um notebook no Wi-Fi) ficaram minutos em 360p e 540p com ~6 Mbps de banda estimada. Não volte para o `balanced` sem refazer esse teste.
    - O risco conhecido: com o descarte de quadros desligado (abaixo), uma queda forte de banda pode encher a fila de envio em vez de baixar a nitidez. Confira o "Fila ms" dos relatórios; se subir nas oscilações, os próximos passos são baixar o bitrate para 2,5 Mbps ou religar o descarte, um de cada vez.
  - **O som da transmissão vai num MediaStream separado do vídeo** (`montarEnvio` manda o áudio sem `streams`; quem assiste junta os dois no `ontrack` de `receberOferta`). Na mesma, o navegador de quem assiste sincroniza som e imagem, e a imagem esperava o som: num celular Android pelo Wi-Fi, o buffer de vídeo ficou entre 550 e 850 ms com a folga pedindo no máximo 250. O preço é o som poder chegar uma fração de segundo depois da imagem no celular.
  - O app desliga o descarte de quadros do WebRTC (`--force-fieldtrials=WebRTC-FrameDropper/Disabled/` no `main.js`). O codificador AMD passa do alvo em cena pesada e o descarte derrubava o envio para 5–9 fps por um segundo, com a captura em 21 (relatório real e A/B com o Path of Exile). Não remova. No navegador, o descarte continua.
  - **Codec: H.265 (HEVC) quando os dois lados conseguem, H.264 de reserva** (`preferirCodecs` em `webrtc.ts`, 17/10/2026). Numa bancada dentro do app (duas conexões no mesmo PC, um print de jogo rolando, 720p a 30 fps, AMD RX 7800 XT, três rodadas de cada): a 4 Mbps, o H.265 deu 32,6–32,8 dB de PSNR usando 3,9 Mbps, e o H.264 31,0–31,1 dB passando do alvo (4,5–4,7 Mbps); o H.265 a 4 Mbps ficou melhor que o H.264 a 6,5 Mbps (32,1–32,4 dB), por ~1 ms a mais de codificação por quadro, os dois na placa (`AMDh265Encoder`, `AMDh264Encoder`). O AV1 e o VP9 deste Chromium (152) codificam **no processador** (13–15 ms por quadro, o atraso dobrou no AV1): não entram sem refazer a medida num Electron novo. O Chromium só oferece o H.265 com a placa codificando (quem transmite) e decodificando (quem assiste): sem isso, a negociação cai sozinha no H.264 (navegadores sem H.265, placas antigas). **Proteção:** se o H.265 for negociado e o codificador não soltar nenhum quadro em 10 s (`conferirHevc` em `cliente.ts`), a conexão é refeita em H.264 e as próximas também, até recarregar. O teste "codec da transmissão" (`conexao.test.ts`) confere a ordem.
    - **Em 1080p, sempre H.264** (`aceitaHevc` em `qualidade.ts`, 17/10/2026). Em 1080p · 60, reconfigurar o codificador H.265 da AMD no meio da transmissão (a subida do bitrate aos 6 s, a janela mudando de tamanho, os ajustes da rede) o fazia devolver um quadro que o WebRTC não reconhecia (*"Frame with no encode started time recordings"*), e a página caía em seguida: uma verificação fatal do Chromium na thread "Media" (código 0xC000001D), sem H.265 no processador para continuar. Achado pelo dono (tela inteira, Alt+Tab, assistindo pelo celular), reproduzido com 30 Alt+Tabs automáticos e o jogo aberto: caiu três vezes em três; sem a subida do bitrate, não caiu; 720p · 30 e 720p · 60 em H.265 e 1080p · 60 em H.264 nunca caíram. Mudando de 720p para 1080p (ou o contrário) no meio da transmissão, as conexões de envio são refeitas, porque o codec fica o negociado. **Como investigar uma queda assim:** o Electron com `--enable-logging=file --log-file=<arquivo> --vmodule=*rtc_video_encoder*=3,*video_stream_encoder*=1` escreve o que o codificador fez antes da queda; o `crashReporter.start({ uploadToServer: false })` guarda o dump (sem símbolos do Electron, ele dá o nome da thread que caiu, no `ThreadNamesStream`).
  - O Opus vai em estéreo pela edição do SDP (`opusEstereo`), aplicada **na oferta e na resposta**. O som do navegador pede `echoCancellation`, `noiseSuppression` e `autoGainControl` desligados, e a faixa vai com `contentHint = 'music'`.
- **Folga de rede adaptativa** (`FolgaAdaptativa` em `folga.ts`, aplicada por `ajustarFolga` em `cliente.ts`): quem assiste pede `jitterBufferTarget` **só no receptor de vídeo**. Começa em 100 ms e fica entre 80 e 250: sobe na hora com o jitter do RTP e +50 ms a cada congelamento, e desce 5 ms/s depois de 10 s de rede calma.
  - Não aplique no som da transmissão: o navegador sincronizava som e imagem (hoje vão separados, veja acima), e a folga do som somada à saída de áudio fazia a imagem esperar ~200 ms a mais (medido num celular Android pelo Wi-Fi: buffer de ~450 ms com som contra ~220 ms sem).
  - Acima do limite da folga, quem segura a imagem é o navegador (o sincronismo ou a espera que ele mesmo aumenta depois de um congelamento). O relatório mede `msBufferSom` e `folgaMs` para separar os dois.
  - Era fixa em 200 ms, por causa de um Wi-Fi com soluços (ida e volta de 8 para 222 ms) que virava congelamentos. Mas os relatórios mostraram que ela era ~96% do atraso. Com a adaptativa, o atraso estimado na bancada caiu de ~195 para ~100 ms.
- **Bitrate inicial** (`BITRATE_INICIAL`/`SUBIR_BITRATE_DEPOIS` em `cliente.ts`): cada pessoa nova recebe com 50% do bitrate da qualidade nos primeiros 6 s. O codificador da AMD passava do alvo no começo (9 Mbps pedindo 4), enchia a fila de envio e congelava a imagem 3 ou 4 vezes logo na entrada.
- **Captura a ~21 fps com o jogo sem limite de fps:** o Chromium espaça as capturas para a cópia de cada quadro não passar de 50% do tempo (`kDefaultMaximumCpuConsumptionPercentage` em `desktop_capture_device.cc`). Limitar o jogo a 60 levou a captura de 21 para 29 fps no Path of Exile. O diagnóstico `captura-lenta` e o aviso "Captura a X fps" dizem isso. Detalhes e o que já foi testado em "Captura de alguns jogos fica abaixo do fps pedido", abaixo. **No app 1.2.18+, a captura padrão é a do app** (veja "Captura de vídeo do app"), sem esse limite; o que segue vale para o navegador e para a captura antiga.
- **Voz** (`voz/`): uma `RTCPeerConnection` só de voz por par de pessoas, separada do vídeo (sem a folga do vídeo, e cair o vídeo não derruba a conversa). O estado fica num *store* próprio (`useVoz`), para o anel de quem fala não redesenhar os vídeos.
  - **Quem chega liga:** no `bem-vindo` (e no `voltei`), a pessoa faz a oferta para todos os `outros`; quem já estava só responde. Assim nunca há duas ofertas ao mesmo tempo. Se a conexão cair, quem ligou liga de novo (até 3 vezes).
  - A sinalização usa as mesmas `oferta`/`resposta`/`candidato`, com `canal: 'voz'` (sem a inversão `envio` ↔ `recebimento`). O servidor não mudou.
  - Mudo e surdo vão por um canal de dados combinado (`negotiated`, id 0) na própria conexão de voz.
  - **Microfone:** `getUserMedia` → `processador.ts` (AudioWorklet, quadros de 10 ms) → `MediaStreamDestination`, cuja trilha vai em todas as conexões. Mudo é `trilha.enabled = false`.
    - O processador aplica o volume de entrada, o RNNoise e a porta (`porta.ts`).
    - O RNNoise é o binário WebAssembly de `@sapphi-red/web-noise-suppressor`, instanciado sem a cola do Emscripten. Ele só importa `emscripten_memcpy_big`, `emscripten_resize_heap` e `__assert_fail`; chame `emscripten_stack_init` **antes** de `__wasm_call_ctors`.
    - O RNNoise roda sempre, mesmo com a supressão "do navegador" ou "desligada", porque a chance de voz dele é o que faz a sensibilidade automática.
  - **Saída:** cada amigo → `GainNode` (volume dele) → mestre (volume de saída; 0 com o som desligado) → `AudioContext` com `setSinkId`. O som da conexão também vai num `<audio muted>`: sem isso, o Chrome não entrega o som do WebRTC ao Web Audio.
  - **Quem fala:** os amigos, pelo `audioLevel` de `getSynchronizationSources()` a cada 100 ms (a porta de quem fala manda silêncio quando a pessoa cala); eu, pela porta aberta.
  - Opus de voz: mono, 64 kbps, FEC e DTX (`opusDeVoz`).
  - **Atalhos** (`voz/atalhos.ts`, aba "Atalhos" em `componentes/Atalhos.tsx`): mudo, som desligado e apertar para falar. Padrão: Ctrl+Shift+M e Ctrl+Shift+D (os do Discord; decisão do dono), apertar para falar sem tecla. As teclas ficam como o `code` do navegador (os modificadores sem lado; `Mouse3` a `Mouse5` para os botões do meio e laterais) e viram teclas virtuais do Windows (`teclaVirtual`) para o app. **No app 1.2.17+, valem com o jogo na frente** pelo auxiliar (veja "Atalhos globais" no app); no navegador e no app antigo, a página escuta o teclado (`LeitorDeAtalhos`, a mesma regra do auxiliar), só com ela em foco. Uma tecla sozinha não dispara com um campo de texto em foco. O Ctrl+Shift+D era do teste de desempenho, que passou para Ctrl+Shift+X.
  - **Apertar para falar** (`apertarParaFalar` nos ajustes): a trilha só fica ligada com a tecla apertada (`voz.falar`), mais `SEGURA_AO_SOLTAR` (150 ms) para não cortar a última palavra. Nesse modo a porta fica aberta (`semPorta` no processador), mas continua aprendendo o ambiente. O anel verde e o "Aperte X para falar" do cartão de baixo seguem a tecla.
  - **Qualidade da conexão com cada amigo** (`voz/qualidade.ts`): a cada 2 s, o `getStats` da conexão de voz (que existe com todos) dá ida e volta, perda e jitter; `MedidorDaConexao` decide boa, instável ou ruim (limites em `LIMITES`). Piora na hora e só melhora depois de 3 leituras (sem piscar); a perda só conta com 50 pacotes ou mais na janela, porque com o amigo calado o DTX manda poucos. A barra lateral mostra o ícone **só quando não está boa**; o menu de voz da pessoa mostra os números.
- **Piso de fps da captura** (`FPS_MINIMO_DA_CAPTURA` = 10): entra por `applyConstraints` (`tamanhoDaCaptura(true)`), porque o `getDisplayMedia` não aceita `min`. Com a tela parada, o Chromium só entrega quadro quando algo muda (até 1 fps) e quem assiste contava congelamentos falsos. Com o piso, o Chromium pede um quadro repetido (`RequestRefreshFrame`, uma captura a mais) quando nenhum chega em 100 ms. Não suba muito: com o jogo limitado a ~21 fps de captura, um piso perto disso gastaria capturas extras.
- **`aquecerWebRtc()`:** o primeiro uso do WebRTC na página trava a thread principal por até 1,6 s (consulta de codecs à placa de vídeo, medido numa RX 7800 XT). A consulta é feita 300 ms depois do `bem-vindo`; sem isso, a trava caía no primeiro "Assistir" e picotava o som do app. Não remova.
- **Vídeo que cai volta sozinho** (`refazerVideo`): a conexão de recebimento em `failed`, ou em `disconnected` por mais de 2 s, é refeita com `deixar` + `assistir` (quem transmite fecha a velha e manda oferta nova). Até 3 vezes seguidas se já tinha conectado; 1 vez se nunca conectou (rede sem TURN), e então o aviso com "Tentar de novo". Sem a sinalização no ar, espera ela voltar, porque a conexão velha ainda pode se recuperar.
- **Relatório** (`relatorio()` em `cliente.ts`, botão "Salvar relatório" nas estatísticas): guarda em memória as últimas 15 mil linhas, que são as `Metrica` de cada segundo e os acontecimentos (todo `avisar` entra sozinho, mais entrar, transmitir, assistir, qualidade, estado das conexões e `refazerVideo`). Nada sai do PC: o arquivo JSON é baixado e a pessoa decide para quem manda. Ao acrescentar um acontecimento importante, chame `registrar`.
- **Teste de desempenho e gravação da sala** (`web/src/desempenho/`). Escondidos de propósito (pedido do dono): sem botão na interface, só pelos atalhos em `Sala.tsx`. Ctrl+Shift+X abre o teste simulado (era o D, que virou o atalho de desligar o som) (tela em `componentes/TesteDesempenho.tsx`, carregada sob demanda com `lazy`); Ctrl+Shift+G começa ou para a gravação da sala (`gravadorDaSala.ts`, `import()` sob demanda). No app, Ctrl+Shift+N troca entre a captura do app e a antiga (veja "Captura de vídeo do app").
  - `gravacao.ts` é o controlador. No modo **simulado**, cria pares de `RTCPeerConnection` no próprio PC (`criarSimulado`, sem servidor: espera juntar os candidatos e troca o SDP direto), montados com `cliente.montarEnvio` e registrados com `registrarEnvioExtra`, para acompanharem `aplicarQualidade` e a troca de fonte. Com uma qualidade só, o roteiro passa por 1, 3 e 7 espectadores. Os vídeos dos simulados precisam estar **na tela**: o `requestVideoFrameCallback` só roda em vídeo desenhado.
  - **Gravação da sala:** quem grava manda `gravar-sala`; o servidor (`Salas.gravador`, uma por sala) avisa todos com `gravacao-da-sala` (vai também no `bem-vindo`, em `gravando`) e passa a repassar as mensagens `medidas` **só** para quem grava. Em cada PC, `coletor.ts` (ligado em `main.tsx` por `acompanharGravacaoDaSala`) mede a cada segundo os envios (`cliente.envios()`) e os recebimentos (`cliente.recebimentos()`), o PC e a página, e manda um `Pacote` (`tipos.ts`) com os ids do servidor. `gravadorDaSala.ts` troca os ids pelos nomes, carimba o `t` na chegada, registra os papéis (quem transmite, para quem, quem assiste) e abre um trecho por transmissão a cada mudança de qualidade, de quantos assistem ou de quantas transmissões a pessoa assiste (`Trecho.assistindo`). Se quem grava reconecta (id novo), ele pede `gravar-sala` de novo.
  - `analiseDaSala.ts` transforma cada transmissão numa `Gravacao` de modo `sala` e passa pela mesma `analisar`; por cima, os diagnósticos da sala inteira (`transmite-e-assiste`, `pc-de-quem-assiste`). `relatorioDaSalaParaIa` (em `relatorioIa.ts`) reaproveita os blocos do relatório do teste, um por transmissão.
  - **As linhas ficam num worker** (`trabalhadorDaSala.ts`): a cada segundo, `mandarLinhas` manda as linhas novas e esvazia as listas da página. O worker gera os arquivos (`arquivosDaGravacao`) fora da thread da página: com 1 hora e 4 pessoas, gerar tudo leva ~0,5 s, o que travaria o vídeo de quem grava. O worker só pode importar código sem DOM (análise e relatórios; nada de `cliente.ts`). A gravação para sozinha em 2 horas (`DURACAO_MAXIMA`, ~60 MB de dados por hora com 4 pessoas).
  - **O relatório para IA tem orçamento:** no da sala, as tabelas de CSV dividem `LINHAS_DA_SALA` (1500) linhas; os segundos vizinhos são juntados com média, mas os picos (`ritmo_max`, maior tarefa) ficam com o máximo, e "Os piores segundos" vão sem média, com o que acontecia em quem transmitia no mesmo segundo (±1 s). Acontecimentos repetitivos são cortados em 30 por tipo. Medido: ~45 mil tokens com 1 hora e 4 pessoas. Não tire o orçamento: sem ele, 10 minutos passavam de 200 mil tokens.
  - Salvar: `ponte.estatisticas.salvar(pasta, arquivos)` (app 1.2.11+, `estatisticas-salvar` no `main.js`) grava em `Documentos\Ozamigos\Estatísticas\<pasta>`, só nomes simples (`nomeSeguro`), via arquivo temporário. A cada 30 s salva o `.md`; no fim, também o `.json` e um `.html` por transmissão. No navegador, baixa no fim.
  - `amostradores.ts` lê o `getStats` (diferença de um segundo para o outro), o ritmo na tela (`MedidorDeRitmo`) e as tarefas longas da página. `analise.ts` tem **todas as regras** dos diagnósticos e da recomendação. Os limites estão escritos lá e no glossário do `relatorioIa.ts`; mudou uma regra, mude os dois.
  - Os primeiros `SEGUNDOS_DESCARTADOS` (8) de cada trecho e o tempo em que espectadores novos se conectam ficam fora das médias.
  - O formato dos dados é `FORMATO` (teste) e `FORMATO_DA_SALA` (gravação da sala) em `tipos.ts`: mudou um campo, suba a versão e confira o relatório para IA.
  - **A captura do app na gravação** (1.2.18, formatos `desempenho/3` e `sala/2`): cada `AmostraCaptura` traz a `origem` (`app` ou `navegador`) e, na do app, `app` com os quadros novos e repetidos e o tempo por quadro do auxiliar (`video-medidas` no `main.js`, a última linha JSON dele), e os quadros que chegaram à página, os que ela pulou e o atraso da captura até ela (`medidasDaPagina` em `videoDoApp.ts`). `completarCaptura` (`amostradores.ts`) junta tudo uma vez por segundo. O diagnóstico `captura-lenta` diz onde a captura do app ficou: no Windows (poucos quadros novos), no auxiliar (mais que meio intervalo por quadro) ou na página (quadros pulados). Conferido numa gravação de verdade: 30 novos por segundo, ~1,2 ms no auxiliar, ~5 ms até a página.
  - Os contadores do Windows são ligados por `contadoresDoPc` (`amostradores.ts`), que conta quem está usando: o teste e a gravação da sala podem medir juntos. O teste simulado não começa com a sala gravando (ele troca a qualidade).
  - **O PC** vem do app (1.2.10+): `ipcMain` `desempenho-pc`, `desempenho-ligar` e `desempenho-amostra` no `main.js`. O processador vem do `app.getAppMetrics` (o `percentCPUUsage` **já é** % do processador inteiro, não divida pelos núcleos). A placa de vídeo vem do `OzamigosSom.exe --contadores` (`desktop/som/Contadores.cs`), que lê os contadores "GPU Engine" do Windows pelo nome em inglês (`PdhAddEnglishCounter`, funciona em Windows em português) e escreve uma linha JSON por segundo. Ele só lê; é desligado no fim do teste e quando a página recarrega.
- **Seletor do app:** abre no clique, em estado "carregando" (`seletorCarregando` em `ponte.ts`), antes de o `main.js` terminar o `desktopCapturer.getSources` (~0,4 s com 7 janelas). Cancelar nesse meio-tempo responde `null` quando a lista chegar.
- **Estatísticas:** `medir()` roda a cada 1 s.
  - O Firefox não informa `qualityLimitationReason`, o fps da captura nem `encoderImplementation`.
  - O Firefox gera ids de relatório novos a cada consulta, então os Mbps são calculados por `tipo:ssrc`.
- **Reconexão automática** (`perderConexao` → `agendarReconexao` → `conectar`; `voltei` no `bem-vindo` seguinte):
  - a queda é detectada pelo `onclose` **ou** pelo silêncio: o servidor responde `pong` a cada `ping` (30 s), e 70 s sem mensagem nenhuma (`SILENCIO_MAXIMO`) derrubam a conexão do lado do cliente;
  - tentativas com espera de 1, 2, 5 e depois 10 s, para sempre; o evento `online` do navegador força uma tentativa, e a página voltar a ficar visível também (no celular, o navegador congela a página em segundo plano e a conexão cai sem avisar; com mais de 35 s sem mensagem, ela é dada como caída na hora);
  - o `bem-vindo` traz uma `ficha` secreta. Na reconexão, o `entrar` a reenvia, e o servidor (`Salas.donoDaFicha`) **tira da sala a conexão antiga** que ele ainda não viu cair (senão sobra uma pessoa fantasma ocupando vaga);
  - **o id muda na reconexão.** Por isso, quem volta é reconhecido **pelo nome** (`saidas`, janela de 2 min): `voltei` fecha todas as conexões WebRTC, reenvia `comecei` se eu transmitia e volta a assistir quem eu assistia; do outro lado, `saiu` + `entrou` com o mesmo nome vira "reconectou", e `compartilhando` dessa pessoa retoma a plateia;
  - durante a queda, as conexões WebRTC abertas **continuam** (o vídeo não passa pelo servidor); elas só são refeitas quando a sinalização volta;
  - recusado ao reconectar (`senha-errada`, `sala-cheia`): desfaz tudo e volta para a entrada com o erro.

- A raiz `/` do servidor é sempre a entrada (o app Electron carrega `/`). No navegador, a entrada tem um link para o site (`SITE` em `Entrada.tsx`).
- **Tela acordada** (`telaAcordada.ts`, ligada no `main.tsx`): com mais alguém na sala, a página segura a tela com a Screen Wake Lock API, como o Discord numa chamada; sozinho, solta. O navegador solta a trava quando a página fica escondida, e ela é pedida de novo quando a página volta. Sem a API (ou recusada), segue sem.
- **Configurações** (`Configuracoes.tsx`, a engrenagem do cartão de baixo): três abas, "Voz e áudio", "Notificações" e "Geral" (versão e servidor). Sair da aba de voz desliga o teste do microfone. A janela tem altura fixa, para não pular de tamanho entre as abas.

- **Chat da sala** (`PainelChat.tsx`, estado em `cliente.ts`: `chat`, `chatAberto`, `chatNaoLidas`; as imagens, abaixo): o painel fica no lugar do de estatísticas, um de cada vez. Com ele fechado, a mensagem vira aviso (uma pessoa mandando várias seguidas troca o aviso anterior, sem empilhar), som e notificação do Windows com a janela atrás do jogo. A página guarda só as últimas 200 mensagens da sessão, na memória. O cliente confere o mesmo freio do servidor antes de mandar, para a mensagem recusada continuar no campo; mudou um limite, mude os dois (`LIMITE_DO_CHAT`, `CHAT_RAJADA`, `CHAT_JANELA`). **O texto do chat não vai para o relatório** (`mostrarAviso` em vez de `avisar`): o relatório é para diagnóstico e as pessoas o mandam para outros.
- **Prévias de links do chat** (`PreviasDeLinks.java`, 17/10/2026): o primeiro link de vídeo ou de canal de uma mensagem (YouTube, Twitch, Kick, TikTok, Streamable, Medal) vira um cartão (`CartaoDoLink` em `PainelChat.tsx`). **Quem busca é o servidor**, uma vez para a sala, e manda `previa` para todos: ninguém da sala acessa o site (nem o IP de quem recebe vai para lá). O YouTube não deixa o navegador buscar o oEmbed (sem CORS), e é melhor assim.
  - **Lista fechada, contra SSRF:** `reconhecer` só aceita os caminhos de vídeo de cada site (um canal não vira cartão); oEmbed para YouTube, TikTok e Streamable, as metatags `og:` da página (remontada com as partes conferidas) para Twitch e Medal. **Canais:** Twitch pela página (`og:title` "Fulano - Live on Twitch" ou, em pt-BR, "Ao vivo na Twitch"; a live e o jogo na `og:description`; a imagem da live em `previews-ttv/live_user_<canal>-640x360.jpg`), Kick pela API pública (`kick.com/api/v2/channels/<canal>`; a imagem da live a Kick recusa com 403, então vêm o banner e a foto, que é WebP: por isso o `imageio-webp` da TwelveMonkeys, achado por `ImageIO.scanForPlugins()` no construtor). Cada prévia tem uma lista de imagens candidatas, e vale a primeira que abrir. `NAO_SAO_CANAIS` tira as páginas do site com cara de canal. **YouTube em quatro degraus:** a API de dados v3 se houver `YOUTUBE_API_KEY` (a feita para servidores: o YouTube recusava o oEmbed e a página ao Render de vez em quando, porque os IPs são divididos com muitos serviços; a chave nunca vai para o log); o oEmbed; se ele recusar (401 quando o dono desliga a incorporação em outros sites, ou um bloqueio de datacenter), a página do vídeo (`og:title`, `og:image` em 16:9, o canal no `itemprop="name"`); sem as duas, a miniatura pública (`i.ytimg.com/vi/ID/hqdefault.jpg`) com "Abrir no YouTube". O motivo de cada falha vai para o log com o site e o código, nunca o link. Redirecionamentos são seguidos à mão, só para hosts da lista (`PAGINAS`); as imagens, só de `IMAGENS`. **Nunca busque um endereço que veio do chat sem passar por essa lista.**
  - A miniatura é reduzida no servidor (até 400 px, JPEG, até 48 KB, `data:` na mensagem); imagens acima de 40 MP nem são abertas; um formato que o Java não abre (WebP) ou a falta da parte gráfica do Java só tira a imagem. Na interface, só entra `data:image/jpeg;base64`.
  - Cache de 200 links por 1 hora (falha, 2 minutos), com uma busca só para pedidos juntos; no máximo 4 buscas ao mesmo tempo, em threads virtuais. O robô se identifica (`OzamigosBot`): a Twitch manda as metatags para ele.
  - **O link nunca vai para o log** (é texto do chat). A política de privacidade fala das prévias (nas duas línguas).
  - Testes: `PreviasDeLinksTest` (a lista, o oEmbed com a miniatura reduzida e o cache, o redirecionamento e a imagem fora da lista) e `umLinkDeVideoNoChatTrazAPreviaParaTodosDaSala` (`SinalizacaoTest`, com um `Buscador` falso: os testes não usam a internet).
- **Imagens do chat** (`imagens/`, 17/10/2026): **vão direto entre os PCs, nunca pelo servidor**, por um segundo canal de dados combinado (`negotiated`, **id 1**, rótulo `imagens`) na conexão de voz de cada par (`voz.ts` chama `trocaDeImagens.conectar`/`desconectar`). O servidor não mudou e não vê nenhuma imagem; nada fica guardado (a página guarda só as últimas `IMAGENS_NA_MEMORIA`, 50 no PC e 20 no celular; as mais antigas viram "saiu da memória").
  - **Só imagem, sempre recomprimida; o arquivo original nunca sai do PC** (decisão do dono). `compressor.worker.ts` abre o arquivo (`createImageBitmap`, com a rotação da foto; de GIF animado, só o primeiro quadro), redesenha (o que apaga os dados escondidos, como o GPS) e comprime com o **libwebp do jSquash** (`@jsquash/webp`), num worker. Não troque pelo WebP do canvas: ele não tem o `use_sharp_yuv`, e linhas finas coloridas desbotavam (o vermelho de um ícone no Factorio); e o Safari devolve PNG.
  - **As regras e os números ficam em `regras.ts`**, usados por quem manda e por quem recebe: até 3,7 MP (2560×1440) e lado maior até 3840; qualidade 85, depois 75 e 65 se passar do teto de **1,5 MB**; se nem a 65 couber (ruído puro), a imagem diminui até caber. Sem perda só em print simples (PNG com poucos bytes por pixel), e fica o menor. Calibrado com prints reais do dono (2560×1440): jogo de 7,5 a 8,7 MB em PNG vira 0,9 a 1,4 MB, em ~0,5 s. O `target_size` do libwebp levava ~2,3 s: por isso as tentativas.
  - **Protocolo** (`protocolo.ts`): texto é controle em JSON (`ola`, `inicio`, `fim`, `cancelar`, `recebi`, `recusei`), binário é pedaço (até 64 KB, ou o `maxMessageSize` da conexão). Uma imagem de cada vez por pessoa (a fila em `troca.ts`), então os pedaços são sempre da última anunciada. **Quem recebe confere tudo antes de mostrar** (`Recepcao`): tamanho dentro da regra, até 2 MB, a soma dos pedaços, e o **cabeçalho do WebP com o tamanho anunciado** (um arquivo que decodificasse em 16000×16000 travaria a página); 20 imagens por minuto de cada pessoa e 60 s para chegar. Tudo o que não bate é jogado fora e respondido com `recusei`.
  - **`ola`:** cada lado manda ao abrir o canal. Quem não diz "olá" em 5 s está com a página de antes das imagens: o canal id 1 não existe nela e o que se mandasse sumiria (medido: a conexão de voz continua de pé, e o canal do mudo continua funcionando). Sem o `ola`, a falha aparecia só no prazo da confirmação (20 s por imagem).
  - **Freios de quem manda:** até 4 imagens por envio, 12 por minuto, e **3 Mbps enquanto a pessoa transmite** (`RITMO_DAS_IMAGENS_TRANSMITINDO`, um balde de fichas dividido entre todos): a conexão de voz não divide a banda com a do vídeo. Na bancada (localhost, sem limite de rede), 4 imagens de 1,5 MB com uma transmissão rodando: nenhum congelamento em quem assistia e o jitter da voz em 0–1 ms. **O efeito num upload de verdade ainda não foi medido**: confira o "Fila ms" das estatísticas de quem transmite mandando um print.
  - **Com texto, o texto vai antes** (`mandarImagens(prontas, texto)`): as imagens só saem quando o servidor devolve o texto (ou em 3 s). Mandando juntos, o texto (pelo servidor) e as imagens (diretas) chegavam em ordens diferentes para cada um.

Com a conexão de voz ainda abrindo ou nem criada (a pessoa acabou de entrar: quem chega liga), a imagem espera até `ESPERA_DO_CANAL` (15 s) em vez de falhar na hora. O relatório registra tamanho, tempo e para quem não chegou, nunca a imagem.
  - Testes: `imagens.test.ts` (regras, cabeçalho e as recusas da `Recepcao`) e o e2e "um print colado no chat chega comprimido ao amigo...".
- **Versão na tela** (`Versao.tsx`, ao lado do logo e embaixo da entrada, em 10 px): a do app (`ponte.versao`, ou "web" no navegador) e o commit de onde a interface saiu (`__COMMIT__`, definido no `vite.config.ts`: `RENDER_GIT_COMMIT` no Render, que o `Dockerfile` recebe como `ARG`; `git rev-parse` no PC). - **Acordar o servidor** (1.2.17, "Acordar o servidor" no `main.js`): o Render gratuito dorme depois de 15 min sem ninguém, e o primeiro pedido fica parado até ele acordar (75 s medidos em 17/10/2026). A janela só aparecia com a página pronta, e o app parecia não abrir. Agora o `main.js` pergunta ao `/actuator/health` antes de abrir a página (`esperarOServidor`): sem resposta em 1,5 s, a tela de início entra no modo "Conectando…" (`?acordando=`), com o tempo e o "Trocar o servidor" (`parar-de-esperar`), sem explicar o porquê (tom de produto); quando ele responde, abre a sala. Qualquer resposta vale, menos 502, 503 e 504 (o Render subindo). Duas falhas de rede seguidas mostram o erro de antes; 3 minutos sem acordar também. Cada espera tem um número (`esperaDoServidor`): trocar o servidor cancela a anterior. O teste da fumaça "com o servidor dormindo..." cobre isso.
- **Captura de vídeo do app** (1.2.18, `desktop/captura/`, `OzamigosCaptura.exe`; na página, `videoDoApp.ts`): **é a captura padrão no app.** O auxiliar captura a janela (pelo HWND, que é o número do id `window:HWND:0` do Chromium) ou a tela (por um ponto no meio dela, em pixels de verdade: `screen.dipToScreenPoint`) pelo **Windows Graphics Capture**, reduz até o tamanho pedido sem mudar a proporção (nunca aumenta; lados pares), converte para NV12 BT.709 de faixa limitada no processador de vídeo da placa (`Conversor.cs`), lê o NV12 para a memória e o escreve na saída padrão. Cada quadro tem um cabeçalho de 24 bytes ("OZQ1", largura e altura em u16, o número em u32, 4 de reserva e o momento da captura em ms, f64). Só sai quadro quando a imagem muda; parada, o último é repetido a cada 100 ms (o mesmo piso de 10 fps da captura do Chromium). Medido sem carga: 30 fps, 1,6–2,6 ms por quadro no auxiliar, ~6–7 ms até o app.
  - **O fluxo:** o seletor (`SeletorDeFonte.tsx`) responde com `captura: { largura, altura, fps }` (da `QUALIDADE`) quando `usarCapturaDoApp()`, depois de montar a trilha (`prepararVideoDoApp`: um `MediaStreamTrackGenerator` que recebe os quadros por `ponte.video.aoReceberQuadro`). O `fonte-escolhida` do `main.js` liga o auxiliar (`ligarCapturaDeVideo`), espera o **primeiro quadro** (até 4 s), e então **recusa o `getDisplayMedia` de propósito** (`responder(null)`) e devolve `{ videoDoApp: true, tipo, fonte }`; o `capturar` do `cliente.ts` troca a tela recusada pela trilha do app. Trocar de fonte reaproveita a mesma trilha (como o som do PC). A página só pede a captura do app se souber montar a trilha: a página de antes, num app novo, segue com a do Chromium.
  - **Volta para a captura do Chromium, sem ninguém clicar:** se o auxiliar não abre (sem o `.exe`, Windows sem WGC, nenhum quadro em 4 s), o `main.js` responde com a fonte, como antes; sem o auxiliar de som, também (o som do Windows inteiro, `loopback`, só vem com a captura do Chromium). No meio da transmissão, o auxiliar que cai ou fica 3 s sem mandar nada (`SEM_QUADROS_POR`) vira `video-parou` com `falhou`: a página captura a mesma fonte pelo `getUserMedia` com `chromeMediaSource: 'desktop'` (`capturarPelaFonte`, que não precisa de clique) e faz `trocarFonte`, sem refazer as conexões; até recarregar, as próximas vão pela do Chromium. A janela que fecha (`IsWindow`, a cada segundo) vira `fechou` e encerra a transmissão, como a trilha `ended` do Chromium. Medido no app (Ana no Electron, Beto num Chromium): matar o auxiliar no meio deixou a transmissão em 29–30 fps, agora "do navegador".
  - **A captura antiga, escondida:** Ctrl+Shift+N na sala (só no app) alterna `ozamigos-captura` no `localStorage` (`'navegador'` = a do Chromium); vale a partir da próxima escolha de fonte, e o aviso diz isso. As estatísticas dizem qual está valendo ("30 fps · do app" ou "do navegador", `cliente.origemDaCaptura`), e o relatório registra "captura do app" ou "do navegador". É para o dono comparar as duas com os amigos (pedido de 17/10/2026). Na mesma bancada, com a placa folgada mas o Path of Exile aberto, a do Chromium deu 21–22 fps e a do app 30.
  - **Por que WGC e não a duplicação da tela (DXGI):** a fase 1 usou a duplicação, que não traz o cursor (viria à parte, para desenhar) e não captura janela. O WGC traz o cursor (`IsCursorCaptureEnabled`) e, no Windows 11, deixa tirar a borda amarela (`IsBorderRequired = false`; o auxiliar diz "borda tirada" na saída de erro). As interfaces WinRT são chamadas **pela vtable** (`Wgc.cs`), sem a projeção do .NET (que pesaria ~20 MB): **ao acrescentar uma chamada, confira o índice no `windows.graphics.capture.idl`** (0–2 IUnknown, 3–5 IInspectable). O pool é `CreateFreeThreaded`, e o laço pega o quadro mais novo a cada 1/fps (`MaisNovo`, descartando os mais velhos); a janela que muda de tamanho refaz o pool (`Recreate`) e o conversor.
  - **Armadilhas:** o `MediaStreamTrackGenerator` existe só na janela neste Chromium (o `VideoTrackGenerator` de worker, não); um `<video>` ligado a uma trilha que ainda não recebeu quadros segura o `load` da página para sempre (visto na bancada); a trilha do app não aceita `applyConstraints` nem tem `displaySurface` (`marcarSuperficie` em `captura.ts`); e **o auxiliar precisa de placa de vídeo** (o processador de vídeo do Direct3D 11 não existe no WARP), por isso a fumaça dele pula no CI. O `.exe` tem ~12,5 MB (self-contained, *trimmed*).
  - **Fase 1, a medição que justificou** (17/10/2026; o código, com a duplicação e o codificador H.265 do Media Foundation, está no commit `3265d2d`): com a placa cheia (a bancada em `desktop/captura/bancada/`: `jogo.js` abre um fractal em tela cheia que se ajusta até ~87 fps com VSync; `chromium.js` mede a captura do Chromium), a 720p·30, o Chromium deu 24,6 fps de média (21 no pior segundo) e a captura própria 28,6 (26), com 0,3 ms por quadro para preparar contra os ~23 ms da cópia do Chromium; o jogo perdeu o mesmo nos dois (~6 fps). **Acima de 30, as duas paravam em ~30–35 quadros novos por segundo** com a duplicação: com a placa cheia, o Windows monta a tela menos vezes. **No jogo de verdade** (Path of Exile, rodada pelo dono): no esconderijo, 30 quadros novos em todos os segundos; num mapa pesado, 28–30, caindo só quando o próprio jogo caía para 21–24 fps. **A captura deixou de ser o gargalo.** No codificador do Media Foundation, **sem o modo de baixa latência, o da AMD segurava 2 quadros (~67 ms)** (`CODECAPI_AVLowLatencyMode`; hoje quem codifica é o WebRTC). Na bancada, **o "jogo" precisa de VSync** (sem ele, a janela não apresentava os quadros), **o número de voltas do shader é um uniform** (como constante, o driver caía), e o jogo e a medição rodam em processos separados.
  - **Fase 2, o transporte** (`bancada/transporte.js`): 30 fps na página, **6,7 ms da captura até a página** (p95 10,9), o `AMDh265Encoder` a 30 fps com os quadros NV12 da memória, e o processador quase parado (auxiliar 0,5%, principal 0,6%, página 1,4%).
  - **Robustez e desempenho (1.2.19, 17/10/2026)**, depois de medir cada parte do caminho:
    - **A leitura da placa não espera** (`Conversor.cs`): `Enviar` põe a conversão e a cópia para leitura na fila da placa, numa de três texturas em rodízio, e `TentarLer` pega o NV12 com `Map` sem esperar (`DoNotWait`). Esperando, com o jogo enchendo a placa, o laço ficava parado até a vez dele na fila. Com as três ocupadas, o quadro fica de fora (`atrasados` nas medidas).
    - **O Windows limitava a captura a ~52 fps** (`MinUpdateInterval`, `IGraphicsCaptureSession5`, Windows 11 24H2 em diante): o intervalo mínimo padrão é 1/60 s, arredondado para os quadros da tela, e num monitor de 155 Hz isso dava um quadro a cada três, 52 por segundo (medido: uma janela a 156 fps chegava a 52, pedindo 60 ou 120). O auxiliar pede metade do intervalo do fps (`IntervaloMinimo`; diz "intervalo mínimo ajustado" na saída de erro): pedindo 60, saem 60; pedindo 120, 120. Os IIDs e a ordem dos métodos das interfaces da captura foram conferidos no `Windows.Graphics.winmd` do próprio Windows.
    - **O laço pega cada quadro quando ele chega** (`Programa.cs`): olha o Windows a cada ~1 ms e manda o mais novo assim que for a vez, sem passar do fps (cada envio marca a vez seguinte um intervalo depois **da vez marcada**, com 10% de folga para adiantar; contada da chegada do quadro, os atrasos se somavam). Depois de mais de um intervalo parado (imagem sem mudar), recomeça da hora de agora. Antes, num ritmo fixo de 1/fps, o quadro esperava o próximo tique e, fora de fase com um jogo a 60, um saía pulado e o seguinte repetido. Com a fonte mais rápida que o fps pedido, os de sobra contam em `pulados`.
    - **A escrita para o app numa thread própria** (`Saida.cs`, fila de dois): escrever um quadro leva ~1–2,5 ms (o cano só esvazia quando o app lê), e o laço ficava parado esperando. Com o app atrasado, o quadro que não cabe na fila fica de fora (`descartados`).
    - **O auxiliar não perde o relógio fino** (`SemEconomiaDeEnergia`): sem janela, o Windows 11 o tinha por invisível, e o `Sleep(1)` virava ~15 ms (o mesmo problema do app, em "Relógio fino com a janela tapada"). Também sai da economia de velocidade (núcleos de economia). E roda com prioridade acima do normal, o laço em `Highest` e a prioridade alta na fila da placa (`SetGPUThreadPriority(7)`, quando o Windows deixa; o auxiliar diz na saída de erro).
    - **Trocar da captura do app para a antiga no meio da transmissão encerrava a transmissão** (1.2.18): fechar a escrita do `MediaStreamTrackGenerator` termina a trilha com o evento `ended`, que é o "parar de transmitir" do `usarTela`. O `pararVideoDoApp` tira o aviso antes de fechar.
    - **A placa que reinicia** (driver caindo, `DeviceRemovedReason`) faz o auxiliar sair com erro: o app troca para a captura do Chromium em vez de repetir a última imagem para sempre.
    - **O horário de cada quadro é o de quando o Windows o entregou ao auxiliar.** O `SystemRelativeTime` do WGC fica uns ms no futuro (é quando a tela vai mostrá-lo) e dava atraso negativo.
    - **O canal direto até a página, com controle de fluxo** (o maior achado): no app 1.2.18, os quadros iam pelo `ipcRenderer` até a thread da página, que em 1080p · 60 (~160 MB/s) não dava conta, e o atraso crescia sem parar: de 13 ms para 2,7 s em 30 s, com a memória do app junto. Agora o `main.js` abre um `MessageChannelMain` (`abrirPortaDoVideo`), o preload passa a porta à página por `window.postMessage` e a página a um worker (`videoDoApp.worker.ts`), que monta o `VideoFrame` fora da thread da página e confirma cada quadro. O app só manda com menos de três a caminho (`QUADROS_A_CAMINHO`); com a página atrasada, o quadro fica de fora (`deixados`) e o atraso não cresce. Uma confirmação perdida destrava em 1 s. O `main.js` lê o cano direto num buffer do tamanho do quadro, reaproveitado (sem `Buffer.concat` nem a cópia para mandar), e nem copia o quadro que vai ficar de fora. A página de antes (sem `captura.canal`) continua recebendo por `quadro`.
    - **As qualidades acima de 720p · 30 só aparecem com o canal direto** (`qualidadesAltas` em `escolhaDeQualidade.ts`, pela `ponte.video.canalDireto`): no app 1.2.18, elas enchiam a thread da página. A escolha fica fora de `qualidade.ts`, que os workers da gravação importam e não pode tocar na ponte (o worker caía com "window is not defined").
    - **No jogo de verdade** (Path of Exile na cidade, 80–120 fps, a janela do jogo, 17/10/2026), sem nenhum congelamento em quem assistia: 720p · 30 a 30 fps (auxiliar 2,2 ms, ~15 ms até a página, 5% do processador no app); 720p · 60 a 60 (2,3 ms, ~11 ms, 8%); 1080p · 30 a 30 (2,7 ms, ~22 ms); 1080p · 60 a 59,6 (2,9 ms, ~20 ms, 14%). A captura antiga, no mesmo lugar, deu 29,7. Num mapa com ação, o próprio jogo fica em ~45 fps e cai para 18–24: a captura acompanha o jogo (ela não cria quadros que ele não desenhou).
    - **Medido (17/10/2026):** sem carga, o auxiliar leva ~2 ms na placa e ~1,1 ms (720p) ou ~2,5 ms (1080p) para escrever, e o laço dá ~620 voltas por segundo. Uma janela que muda de tamanho, minimiza (repete a cada 100 ms), volta e fecha passou sem nenhum quadro estragado. Dois minutos em 1080p · 60: 6.462 quadros, memória estável (83 → 76 MB). No app, com o Path of Exile ocupando ~71% da placa e o PC a 74% do processador: 720p · 30 a 30 fps e ~18 ms até a página; 1080p · 60 a 49 fps de 52 que a tela mudava, ~19 ms até a página, ~1 quadro por segundo deixado de fora e ~14% do processador no app. **O atraso até a página inclui a espera pela vez do quadro** quando a fonte é mais rápida que o fps pedido (a 30 fps com a tela mudando 52 vezes por segundo, ~9 ms em média): é amostragem, não fila, e acontece em qualquer captura.
    - **A bancada do canal** (`bancada/vazao.js`): quadros NV12 do processo principal até a página por três caminhos (o `ipcRenderer`, uma porta na página e uma porta num worker), com controle de fluxo. Sozinhos, os três dão 60 fps em 1080p; a diferença aparece com a página ocupada (a sala de verdade).
  - **Ainda não medido:** a captura da **janela** do jogo com a placa cheia (o WGC pega a janela antes da montagem da tela e pode passar dos ~30–35 da duplicação), e acima de 30 fps.
- **Atalhos globais** (1.2.17, `OzamigosSom.exe --atalhos`, em `desktop/som/Atalhos.cs`): a página manda as teclas (`ponte.atalhos.definir`, `atalhos-definir` no `main.js`) e recebe `mudo`, `surdo`, `falar 1` e `falar 0` (`atalho`). O auxiliar pergunta ao Windows o estado das teclas a cada ~10 ms (`GetAsyncKeyState`). **Não troque pelo `globalShortcut` do Electron nem pelo `RegisterHotKey`:** eles tomam a tecla para si (o jogo deixaria de recebê-la) e não contam quando ela é solta, o que o apertar para falar precisa. Um jogo aberto como administrador esconde as teclas de quem não é (o mesmo no Discord). O auxiliar morre com a entrada fechada e é desligado a cada navegação, como os outros; a página manda os atalhos de novo ao abrir. O teste da fumaça "os atalhos de voz chegam à página..." aperta a F24 (que nenhum teclado tem) pelo `keybd_event`.
- **Endereço do servidor, em ordem de prioridade:**
  1. a variável `OZAMIGOS_SERVIDOR`;
  2. o `configuracao.json` em `%APPDATA%\Ozamigos Share`, gravado pela tela de início (a pasta guarda o nome antigo de propósito: veja "Marca");
  3. `ozamigos.servidor` no `desktop/package.json`.
- O app só aceita `https://`, ou `http://` para `localhost`.
- **Seletor de fontes:** `setDisplayMediaRequestHandler` lista as fontes e manda `escolher-fonte` para a página; o `SeletorDeFonte.tsx` responde com `fonte-escolhida` (`invoke`), que devolve `{ somDoApp }`.
- **Som do PC sem eco** (`desktop/som`, C#):
  - O `OzamigosSom.exe` usa o *loopback* de processo do Windows (`ActivateAudioInterfaceAsync`, `VAD\Process_Loopback`, modo INCLUIR). O Windows só aceita **um processo por captura**, por isso o auxiliar captura cada processo que toca som, menos os excluídos (Discord por nome; o app pelo PID principal, com toda a árvore de processos), e mistura tudo.
  - **Regras da árvore de processos:**
    - capturar um processo leva junto os filhos dele;
    - quem tem um processo excluído entre os descendentes fica de fora;
    - quem é filho de outro processo já capturado não é capturado de novo, para o som não sair dobrado.
    - Os PIDs são validados pela hora de criação, porque o Windows reaproveita números.
  - **Saída:** float32 estéreo, 48 kHz, intercalado, em blocos de 10 ms, pela saída padrão. A saída de erro manda `pronto` (quando começou) ou `sem-suporte`. **Entrada padrão fechada faz o auxiliar terminar**, e é isso que garante que ele morre junto com o app.
  - No `main.js`, o caminho do áudio é: `ligarAuxiliarDeSom()` (que nunca abre dois ao mesmo tempo), depois os quadros inteiros de 8 bytes vão por IPC (`som`) até o `somDoApp.ts`, onde um `AudioWorklet` (com reserva de 40 ms e corte acima de 150 ms) vira um `MediaStreamTrack` adicionado à tela capturada.
  - **Fallback:** se o auxiliar não subir (Windows antigo), o `main.js` responde com `audio: 'loopback'`, que é o som do sistema inteiro.
- **Relógio fino com a janela tapada** (1.2.14, `honrarRelogioFino` no `main.js` e `OzamigosSom.exe --relogio <pid>` em `desktop/som/Relogio.cs`): ao abrir, o app pede ao auxiliar que marque o processo principal com `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` (`SetProcessInformation`). Sem isso, com outro app entre o jogo e o Ozamigos (o navegador aberto antes de voltar para o jogo), o Windows 11 dava o app por invisível e, depois de uns segundos, ignorava o relógio fino dele: a captura, que roda no processo principal e pede um quadro a cada 33 ms, só acordava no tique padrão de 15,6 ms (a cada 46,9 ms) e ficava em ~21 fps com a placa folgada. Com o Ozamigos logo atrás do jogo, ficava normal (achado do dono, 15/10/2026). Não tire sem medir de novo.
  - **Confirmado numa bancada que reproduz sempre** (15/10/2026): um app de teste capturando a tela inteira, com a janela **minimizada** (tapar por outras janelas nem sempre convence o Windows; minimizar convence). Uns 25–30 s depois de minimizar, o `setTimeout` de 1 ms do processo principal passa a demorar ~15 ms e a captura cai para 17–22 fps, e continua assim por um tempo depois de a janela voltar. Com a marca, 40 s minimizado com o relógio em ~1 ms e a captura em 29–30. Refaça essa bancada a cada Electron ou Windows novo.
  - O teste da fumaça "o Windows continua dando o relógio fino ao app..." confere a marca no processo principal (`GetProcessInformation`, pelo PowerShell). O PID é o de `process.pid` dentro do app: o `app.process()` do Playwright é outro processo.
  - O projeto OpenScreen chegou ao mesmo diagnóstico e à mesma saída para os auxiliares de captura dele (PR #927 de getopenscreen/openscreen).
  - Os COM do Windows são chamados **por índice da vtable** (`Com.Metodo(obj, i)`), sem a interop embutida do .NET, para o `.exe` poder ser *trimmed*. **Ao acrescentar uma chamada, confira o índice no cabeçalho do Windows** (0–2 são as funções básicas de COM).
  - A lista de exclusão é `SEM_SOM_DE`, em `desktop/main.js`.
- **Bandeja** (1.2.13, `criarBandeja` no `main.js`): ícone perto do relógio com "Abrir o Ozamigos" e "Sair". O X da janela só a esconde (`fecharParaBandeja()`, ligado por padrão; desliga em Configurações → Geral pela `ponte.bandeja`), e a conversa e as transmissões continuam. Na primeira vez, uma notificação explica onde o app foi (`avisouDaBandeja` no `configuracao.json`).
  - **`saindo` é o que deixa a janela fechar de verdade:** vira `true` no `before-quit` (Sair, `quitAndInstall` da atualização) e no `session-end` (desligar o Windows). Não tire: sem ele, a atualização e o desligamento ficam presos na janela escondida.
  - `second-instance` mostra a janela, mesmo escondida.
- **Mensagens não lidas na barra de tarefas** (1.2.13): a página manda `nao-lidas` (o `chatNaoLidas`, por `avisoNaBarra.ts`); o `main.js` põe um ponto verde no ícone da barra de tarefas (`setOverlayIcon`, desenhado em pixels por `pontoVerde`), o número na dica da bandeja, e pisca o ícone (`flashFrame`) quando chega uma nova com a janela fora de foco. Para de piscar ao focar a janela ou com tudo lido. O `chatNaoLidas` conta o que chega com o chat fechado ou a janela fora de foco, e zera ao voltar para a janela com o chat aberto.
- **Atualização automática** (`atualizarSeHouver()`, com `electron-updater`):
  - Ao abrir, antes da janela principal, o app confere o `latest.yml` da última release do GitHub (`build.publish` no `desktop/package.json`), com prazo de 6 s.
  - Havendo versão nova, mostra a janelinha `atualizando.html`, baixa e chama `quitAndInstall(true, true)`: instala sem tela e reabre o app.
  - Sem internet, sem versão nova ou com erro, segue abrindo normal; a próxima abertura tenta de novo.
  - Só no app instalado: em desenvolvimento (`!app.isPackaged`) e na versão portátil (`PORTABLE_EXECUTABLE_DIR`) não faz nada.
  - **Não feche o aviso antes de criar a janela principal**: sem janelas, o `window-all-closed` encerra o app.
  - O app não é assinado: o updater confere só o SHA-512 do `latest.yml`. Não configure `publisherName`, ou toda atualização vai falhar.

## Como testar (sem câmera nem jogo)

- **Várias pessoas num PC só:** abra várias abas em `http://localhost:<porta>/?sala=Teste01`.
  - Para simular a tela, troque `navigator.mediaDevices.getDisplayMedia` por uma tela falsa: um `OffscreenCanvas` num *Worker* gerando `VideoFrame`, que alimenta um `MediaStreamTrackGenerator`, mais um oscilador de `AudioContext` para o som. Com o painel escondido, um canvas comum na thread principal fica preso a 1 fps.
  - Para preencher campos do React, use o *setter* nativo de `value` e dispare o evento `input`.
- **Abas em segundo plano** mostram fps de recebimento perto de 0, porque o Chrome não decodifica vídeo de aba escondida. Para medir fps, use a aba da frente.
- **Electron:** rode `npx electron . --remote-debugging-port=9333` com `OZAMIGOS_SERVIDOR=http://localhost:<porta>` e controle a janela pelo CDP (`/json`, depois `Runtime.evaluate` e `Page.captureScreenshot`).
  - **Se o Ozamigos instalado estiver aberto, isso não funciona e é perigoso:** o app do repositório usa a mesma pasta de dados (`%APPDATA%\Ozamigos Share`) e, com ela, a mesma trava de instância única. Ele fecha na hora e traz a janela do dono para a frente; se abrisse, gravaria nome, senha e posição por cima dos do dono. Abra por um script que troca a pasta antes de carregar o `main.js`: `app.setPath` embrulhado para devolver outra pasta em `userData`, e depois `require('<repo>/desktop/main.js')`.
- **Medir a transmissão:** duas janelas do Electron (uma transmite, outra assiste) e `getStats` a cada segundo: `framesPerSecond` e `frameHeight` de quem recebe, `encoderImplementation`, `qualityLimitationReason` e o fps da `media-source` de quem envia.
  - Para ver o `encoderImplementation`, a página precisa ter um microfone em uso (o Chrome esconde o dado sem isso). Mas **não use `--use-fake-ui-for-media-stream` ao medir captura**: ele troca qualquer tela por uma tela falsa de 20 fps.
  - Uma fonte desenhada dentro da própria página (o Worker da tela falsa) fica mais lenta com a janela minimizada. Para medir minimizado, capture uma janela de verdade pelo `desktopCapturer`: com ela, a transmissão segue a 60 fps minimizada.
  - A janela aparece na tela do dono, que pode interagir com ela.
  - Ao clicar em botões que dependem de estado do React, espere uns 300 ms (o botão Transmitir do seletor só habilita depois de escolher uma fonte).
- **Som sem eco:** toque tons diferentes em processos diferentes (por exemplo, `Media.SoundPlayer` no PowerShell com WAVs de 440 Hz e 1200 Hz). Para simular o Discord, use uma cópia do `powershell.exe` renomeada para `Discord.exe`. Depois meça com `AnalyserNode` em quem recebe, silenciando o vídeo na aba de teste. **O navegador de teste também é capturado se não estiver silenciado**, e o som recebido volta para a transmissão.
- **Simular o deploy:** clone limpo; em `web`, `npm ci` e `npm run build`; na raiz, `mvnw -DskipTests package`; rode o jar com `PORT=10000`. O handshake do WebSocket deve dar 101 com a mesma origem e 403 com uma origem estranha.

## Armadilhas conhecidas

- **Endereço do servidor guardado:** o `servidor` do `configuracao.json` vence o padrão do instalador, e desinstalar não apaga essa pasta. Por isso:
  - quem escolhe o endereço que já é o padrão não o tem guardado (`salvar-servidor`), e assim acompanha as mudanças de padrão;
  - **ao trocar o endereço oficial, ponha o antigo em `SERVIDORES_APOSENTADOS`** (em `main.js`). Quem o tiver guardado volta sozinho para o novo. Isso aconteceu na troca de `ozamigos-share-app.onrender.com` para `ozamigos.onrender.com`.
- **Os comandos do agente podem ver outra cópia do `%APPDATA%`:** num ambiente isolado (sandbox), o `configuracao.json` lido pelo terminal pode não ser o mesmo que o app usa quando aberto pelo atalho. Para ler o arquivo real, use um `.bat` aberto pelo `explorer.exe`, ou o inspetor do processo principal (`Ozamigos.exe --inspect=9229`).
- **Cache da interface:** o jar data todos os arquivos de 1980. Sem regra de cache, o navegador e o app guardavam o `index.html` por anos e mostravam a interface antiga depois de um deploy. Isso aconteceu na 1.1.1. Hoje há três proteções, **não remova nenhuma**:
  - o servidor manda `Cache-Control: no-cache`, sem `Last-Modified`, para tudo; só `/assets/**`, que tem hash no nome, recebe cache de um ano (`CacheConfig` e `application.properties`);
  - o app abre a página com `cache-control: no-cache` no pedido;
  - na primeira abertura de cada versão, o app apaga o cache HTTP (`limparCacheSeAtualizou`, com a versão anotada em `versaoDoCache` no `configuracao.json`). O `localStorage` não é apagado.
- O `.gitignore` da raiz ignora `build/`. A pasta `desktop/build/` (o ícone) é liberada com `!desktop/build/`. Arquivos novos nela continuam entrando.
- `src/main/resources/static/` é gerada pelo build e ignorada pelo git. Se `localhost` der 404, falta rodar `npm run build` em `web`.
- **Não rode `npx @electron/asar extract-file` dentro de `desktop/`:** ele grava `package.json` na pasta atual, por cima do arquivo real. Para inspecionar o `app.asar`, use `grep -a` ou extraia numa pasta temporária.
- Nos *heredocs* do Git Bash, `\\n` e `\\r` viram quebras de linha reais no Python ou no JS gerado. Para editar código, use as ferramentas de edição ou scripts em arquivo.
- **"Live" no Render não garante a interface nova:** em 14/10/2026, o deploy do `0b9b188` apareceu como "Live" servindo a interface da 1.2.12 (o deploy seguinte saiu certo). Desde então, o `ARG RENDER_GIT_COMMIT` no `Dockerfile` faz a etapa da interface ser refeita a cada commit, sem depender do cache. Depois de um deploy, confira o commit ao lado do logo; se vier o antigo, use *Manual Deploy* → *Clear build cache & deploy*.
- O Render Free dorme depois de 15 min sem tráfego. O `ping` do WebSocket a cada 30 s mantém o serviço acordado com alguém na sala (isso ainda não foi medido por mais de 15 min). Um deploy reinicia o servidor e derruba as salas, mas as transmissões P2P já abertas continuam.
- O instalador não tem assinatura digital, então o SmartScreen avisa na primeira vez.

## Limitações conscientes (não são bugs)

- Sem TURN: CGNAT, 4G/5G e redes corporativas podem não conectar.
- Uma senha por servidor, com freio de 10 senhas erradas por endereço em 5 minutos (`TentativasDeSenha`), mas sem senha por sala: o projeto não serve para uso público aberto sem antes mudar isso.
- Na reconexão, a pessoa ganha outro id e é reconhecida pelo nome. Dois amigos com o mesmo nome podem confundir a volta automática.
- Recarregar a página (Ctrl+R) não é reconexão: é uma entrada nova, e a volta automática a assistir não sobrevive a isso.
- Salas em memória, num servidor só.
- **Captura de alguns jogos fica abaixo do fps pedido.** Com o Path of Exile (RX 7800 XT, tela 2560×1440), a captura do Chromium entrega ~21 fps fixos, tanto da janela quanto da tela inteira, enquanto uma janela comum de 1920×1080 sai a 60 fps com o jogo aberto. Cada quadro do jogo custa ~23 ms para copiar, e o Chromium nunca deixa a captura ocupar mais da metade do tempo (`DesktopCaptureDevice`). Testado e **descartado** como causa ou solução: o uso médio da placa de vídeo (95%, 79% e 57% dão os mesmos ~21 fps), iluminação global e sombras, prioridade de GPU alta (`D3DKMTSetProcessSchedulingPriorityClass`, A/B alternado: 21,5 contra 21,5; refeito numa bancada em 2026-10-14, de novo sem ganho), prioridade de processo e as chaves `AllowWgc*`.
  - **O que funcionou (2026-10-14):** VSync ligado + limite de 60 fps no jogo, em tela cheia em janela: a captura foi de 21 para 28,7 fps. Sem limite, o jogo apresentava ~100 fps com a placa a 99%, e a cópia de cada quadro esperava na fila dela.
  - **Captura em textura, testada e quebrada no Electron 44.7.2 (Chromium 152):** `enable-features=WebRtcAllowWgcUsingTexture,ZeroCopyDesktopCapture` leva a captura de 18 para 29 fps numa bancada com a placa cheia, mas **derruba a página** quando o vídeo passa pelo codificador do WebRTC; só o `ZeroCopyDesktopCapture` não entrega nenhum quadro. Não ligue sem refazer o teste numa versão nova do Electron. A bancada: uma janela WebGL 2560×1440 a ~100 fps com a placa a 99% e o app de teste capturando por uma conexão WebRTC local (contar os quadros e conferir que a imagem não é preta). O app avisa (`capturaAbaixo` em `qualidade.ts`: "Captura a N fps" nos controles e a explicação nas estatísticas). A captura presa em ~21 fps com a placa folgada é outra coisa: o relógio do Windows (veja "Relógio fino com a janela tapada"). Caminho não testado: o modo de janela do jogo (planos de sobreposição/MPO, formato de 10 bits). **A saída foi a captura própria** (1.2.18, "Captura de vídeo do app"): 28–30 fps no Path of Exile.
- O volume é lembrado por nome; dois amigos com o mesmo nome dividem a configuração.

## Fluxo de versão do app

- Mudou `web/` ou `src/`: basta o push na `main`. A interface do app de todos se atualiza.
- Mudou `desktop/`:
  1. aumente `version` em `desktop/package.json`;
  2. faça commit e push;
  3. crie e envie a marca: `git tag vX.Y.Z` e `git push origin vX.Y.Z`.
  - O workflow `.github/workflows/release.yml` (máquina `windows-latest`) confere se a marca bate com a versão, roda `npm ci` e `npm run instalador` em `desktop/` e cria a release com os dois `.exe` (se a release já existir, só troca os arquivos).
  - O `npm run instalador` usa `--publish never`: quem publica é o `gh` do workflow, não o electron-builder.
  - **A release precisa ter o `latest.yml` e o `Ozamigos-Instalador-X.Y.Z.exe.blockmap`**, além dos `.exe`: sem eles, nenhum app instalado se atualiza. O workflow já envia os quatro.
  - Para refazer os arquivos de uma release que já existe: aba *Actions* → *Release do app* → *Run workflow*, escolhendo a tag em *Use workflow from* (`gh workflow run release.yml --ref vX.Y.Z`).
  - Registre a versão no `CHANGELOG.md` (mesmo texto das notas da release, no formato Keep a Changelog).
  - O workflow `ci.yml` roda em cada push na `main` e em cada PR: build da interface, `mvnw test` e `node --check` nos scripts do app.
  - O repositório é público, então o Actions não tem custo. Mesmo assim, não cadastre forma de pagamento: o dono não aceita nenhum risco de cobrança.
